Does an agent's Agent(type, …) allowlist apply when the agent runs as a subagent?

Question

Claim under test, from code.claude.com/docs/en/sub-agents, section “Restrict which subagents can be spawned” (checked 2026-11-14):

When an agent runs as the main thread with claude --agent, it can spawn subagents using the Agent tool. To restrict which subagent types it can spawn, use Agent(agent_type) syntax in the tools field.

This is an allowlist: only the worker and researcher subagents can be spawned. If the agent tries to spawn any other type, the request fails and the agent sees only the allowed types in its prompt.

The Agent(agent_type) allowlist syntax applies only to an agent running as the main thread with claude --agent. In a subagent definition, listing Agent in tools lets that subagent spawn subagents of its own while the depth limit allows it, but any type list inside the parentheses is ignored.

Related, from “Let subagents spawn their own subagents”: By default, a subagent can spawn subagents of its own, up to three layers below the main conversation.

Confirmed if the same agent definition (tools: Agent(allowed-worker)) blocks a non-listed type and lists only the allowed type when it is the main thread (--agent), but can spawn both types and sees every type when it is invoked as a subagent. Refuted if the subagent run also blocks the non-listed type, or if the main-thread run lets it through.

Run mode: headless claude -p only (as asked). Agent SDK and interactive mode are not tested.

Setup

scenario main-thread:  claude -p --agent gate
  gate (main thread, tools: Agent(allowed-worker))
    --Agent--> allowed-worker   (expected: runs)
    --Agent--> blocked-worker   (expected: refused)

scenario subagent:     claude -p   (default main thread, no --agent)
  main --Agent--> gate (depth 1, tools: Agent(allowed-worker))
                    --Agent--> allowed-worker  (depth 2, expected: runs)
                    --Agent--> blocked-worker  (depth 2, expected: runs, list ignored)
  • .claude/agents/gate.md: the agent under test, tools: Agent(allowed-worker). The same file is used in both scenarios; only how it is launched changes.
  • .claude/agents/allowed-worker.md and blocked-worker.md: reply only with their own unguessable WORKER_TOKEN (40718263 and 95136027). A token in gate's tool result proves that worker really ran.
  • prompts/gate.md: gate's script: spawn allowed-worker, then blocked-worker (even if it expects failure, no substitution, no retry), then report both results verbatim. In main-thread it is the -p prompt.
  • prompts/main-spawns-gate.md: in subagent, the default main thread spawns only gate and passes it the same script.
  • allowlist-cli.ts: the driver. It spawns the installed claude -p --output-format stream-json --verbose --model sonnet --setting-sources project --allowedTools Agent Read --permission-mode dontAsk (plus --agent gate in main-thread). Agent is pre-approved, so a refusal cannot be a hidden permission prompt. From gate's own transcript (the main .jsonl, or subagents/agent-<id>.jsonl) it reads:
    • the agent types gate is told it can spawn (agent_listing_delta attachments),
    • whether the Agent tool is sent to the API for gate (api-request-shape),
    • every Agent tool_use of gate and its tool_result (error flag, text, token).
    It also logs PreToolUse / PostToolUse / PostToolUseFailure / SubagentStart / SubagentStop hooks, whose agent_id shows which thread made each Agent call, and the spawnDepth of every subagent from subagents/*.meta.json.
  • Env: CLAUDE_CONFIG_DIR and CLAUDE_CODE_PROJECT_DIR_NAME=sessions from the harness; inherited CLAUDE* vars are stripped. No CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH, so the default depth limit applies.

  • main-thread: the refusal fires after the PreToolUse hook, as a PostToolUseFailure, and no SubagentStart or transcript for blocked-worker exists, so blocked-worker never started. The error reads “not found”, not a permission denial: as main thread, gate simply cannot see any other type. Its agent_listing_delta holds a single line, the allowed-worker one, matching “the agent sees only the allowed types in its prompt”. Cost $0.017.
  • subagent: the hooks attribute both worker spawns to subagent gate (they carry gate's agent_id), not to main, so the depth-2 workers were spawned by gate itself. gate's listing is the full one; its own line even reads (Tools: Agent(allowed-worker)), yet blocked-worker went through. Cost $0.051.
  • Surprising, minor: as a subagent, gate is shown gate itself among the spawnable types, so a subagent could in principle spawn another copy of itself until the depth limit.

Conclusion

On Claude Code 2.1.325 with claude -p, the doc claim holds. tools: Agent(type, …) in an agent's frontmatter is enforced only when that agent is the main thread via --agent: other types are hidden from its listing and a call to one fails with “Agent type '…' not found”. When the very same agent is invoked as a subagent, the parenthesised list is ignored: Agent(…) acts like bare Agent, the subagent sees every agent type and can spawn any of them (within the nesting depth limit). To stop a subagent from spawning, the docs' remedy is to omit Agent from its tools or put it in disallowedTools; to block specific types everywhere, use permissions.deny with Agent(name). Neither was tested here.

Note on --agents (the JSON flag that defines subagents): it only defines agents; it does not make one the main thread. An agent defined with --agents and then invoked as a subagent is in the same position as the subagent scenario here; this run used file-based agents only.
