How far is p50k_base from Claude's real token count?

Question

The c4 session analyzers (tests/vscode/resources/session-analyzers/claude-code/report.mjs and vs-code-harnesses/report.mjs) estimate Claude tokens offline with a vendored gpt-tokenizer 4.0.0, encoding p50k_base. The header of report.mjs justifies it with a third-party claim (propelcode.ai):

you can approximate Claude token counts using OpenAI's tiktoken with the p50k_base encoding

Testable form: on the texts a Claude Code session is made of (sentences, prompts, assistant text, tool inputs, tool results, JSON, code), does p50k_base agree with the count Anthropic's API returns, and if not, does it underestimate or overestimate, by how much, and does it depend on the kind of text and on the model? It holds if Σp50k / ΣClaude is close to 1 with a small spread. It is refuted by a systematic bias. No Claude Code session is involved: this needs only the API, so there is no Agent SDK, claude -p or interactive mode.

Setup

corpus/corpus.jsonl (385 frozen texts)
   ├─ p50k:   vendor/gpt-tokenizer  countTokens(text)
   └─ Claude: POST /v1/messages/count_tokens  {model, messages:[{role:user, content:[{type:text, text}]}]}
              minus the message framing, count("x") − 1, measured once per model
  • vendor/gpt-tokenizer/: a copy of the c4 vendored tokenizer under test (diff -r identical, c4 commit 89c9b8c7e, 2026-10-26). esm/encoding/p50k_base.js is the entry point that report.mjs imports.
  • corpus/sentences.json: 16 English and 16 Italian sentences written for this test, from a single word to ~130 words (chat replies, code review, news, GDPR text, a short story, setup steps).
  • build-corpus.ts: builds corpus/corpus.jsonl once; the file is committed, so every rerun counts the same texts. Sources, all from this repository:
    • the session logs of the other investigations: user prompts, api-request-blob context texts, assistant text, tool_use inputs (JSON.stringify(input), as report.mjs counts them), tool_result payloads grouped by tool, Claude Code system-prompt blocks and tool definitions from api-request-shape, raw log lines;
    • their results folders: stream-json timeline lines, run.json / verdict.json / settings.json pretty and minified, summary markdown;
    • repo files (drivers, lib, CLAUDE.md, REPORT.html) and tool results generated from them in Claude Code's formats: Read (<n>\t<line>), Bash (git log/show/diff, ls), Grep (path:line:text and file lists), Glob.
    Per category, duplicates are dropped and items ordered by sha256, then up to 6 per length bucket (<200, 200–1k, 1k–5k, 5k–20k, ≥20k chars) are taken: 385 texts, 2,165,019 chars, 20 categories.
  • compare.ts: the driver. It counts every text with p50k and with count_tokens for each model, authenticated with the OAuth token Claude Code is logged in with (claudeAiOauth.accessToken from .claude-home/.credentials.json, synced by beginRun(); Authorization: Bearer, anthropic-beta: oauth-2025-04-20, anthropic-version: 2023-06-01; no API key). It retries on 429/5xx. It writes items.jsonl (per text), compare.verdict.json and compare-summary.md. A chars/4 estimate is reported as a baseline.
  • Models: claude-opus-5-5, claude-sonnet-5-5, claude-haiku-5-5, claude-fable-5-2, plus claude-opus-4-7 and claude-sonnet-4-5 to see the tokenizer change between generations.
  • Env vars: none. Options: --models a,b, --concurrency N (default 4), --limit N. After the first run claude-fable-5-2 was dropped from the default models at the user's request; its counts were identical to the other 5.x models anyway (the run.json hash of compare.ts marks the change).
  • pieces.ts: cuts a transcript into those pieces; shared by sessions.ts and explain.ts (it was moved out of sessions.ts after the sessions run, with no change in behaviour).
  • explain.ts: why the sessions differ from the corpus. It reuses the counts of the latest compare and sessions runs (the session texts are re-read in memory and matched by sha256) and does three things. It compares the same categories across the two datasets and re-weights by mix. It regresses log(Claude/p50k) on text features, weighted by Claude tokens, and splits the gap by feature. It counts 21 synthetic probes, one kind of text each, with both tokenizers (21 requests).
  • sessions.ts: the same comparison on real Claude Code sessions given as paths (a <id>.jsonl plus its <id>/subagents/). Each transcript is cut into the pieces report.mjs tokenizes, with the same text: user prompts, assistant text, tool_use inputs, tool_result payloads per tool, prompt_snapshot system sections and tool definitions, attachments (instructions, skill and agent listings, MCP instructions, deferred tools, context). Every occurrence counts, as in report.mjs; Claude counts are cached per distinct text. One model (--model, default claude-sonnet-5-5, the model the sessions ran on). The texts are private and are not written: sessions.items.jsonl holds only a sha256 prefix, transcript, category, label, length and the two counts.

Surprises

  • English prose is underestimated most, Italian least. English sentences 0.69, Italian sentences 0.85. On Sonnet 4.5 it was the other way round: English 0.97, Italian 1.19 (p50k overestimated Italian). The new tokenizer splits English much more finely (3.16 chars/token against 4.44 before), while Italian barely changed.
  • The worst texts are synthetic. The five extremes (ratio ≈ 0.47) are fixture filler from other investigations: a *_MARK_* marker followed by random capitalised English words ("Tunnel candle mosaic kernel compass walnut…"). These 16 filler texts sit at 0.516; without them the 369 real texts give 0.785 (×1.274). On Sonnet 4.5 the filler was 0.898.
  • The best texts are pretty-printed JSON and Grep output (0.85 and 0.83). Indentation and paths tokenize in a similar way under both tokenizers.
  • One global factor is not enough per text. Multiplying p50k by 1.286 leaves a mean absolute error of 9.4% per text (median 6.8%, p90 21.4%). On totals of mixed content the error is much smaller, because category factors range from 1.17 (json-pretty, Italian) to 1.76 (user prompts).

Why the sessions are further off than the corpus (explain.ts)

explain-summary.md. The 16 synthetic filler texts are left out of the corpus, which brings it to ×1.274; the sessions are at ×1.383. No new counts were needed for the real pieces: the session texts were re-read in memory and matched to the counts already taken.

  • On the categories both datasets have, the corpus gives ×1.309 and the sessions ×1.360. Weighting the corpus ratio of each category with the sessions' mix gives ×1.358. Taken one by one, categories differ in both directions (user prompts and assistant text are lower in the sessions, Read and Bash results higher), and on average they compensate.
  • The corpus has a lot of Read and Bash output (25% of its tokens, at ×1.21–1.22). The sessions have much more text written for the model: instructions, system prompt, tool schemas, listings.

2. Text features. A weighted regression of log(Claude/p50k) on text features (R² 0.53; the features are correlated, so the split is indicative) explains 88% of the gap:

  • Density of English words, 40% of the gap. 61% of the session tokens are in pieces of English prose, against 25% in the corpus. English prose is where the new tokenizer departs most from p50k (×1.42 in both datasets).
  • Longer words, 18%. Mean word length is 5.30 against 5.04.
  • Less indentation, 16%. Indentation pulls the ratio down. 12.6% of the corpus tokens are heavily indented, against 0.7% in the sessions.
  • Twice as many uppercase letters, 14%. These are the camelCase tool and member names (caipC4ModelerGetArtifactSlice…).
  • Hex/UUID runs: 5%.
  • Accents and Italian words play no part: 98% of the tokens are in pieces with almost no accented letters.

The new tokenizer splits camelCase identifiers, minified JSON, paths and English words into many more pieces than p50k does. On hashes, UUIDs, numbers and indented JSON the two are close. On tabs and accented letters, where p50k is very inefficient (it falls back to bytes), it is p50k that overestimates, by almost 2×. The corpus has more of the second group (Read/Bash output with indented code, pretty JSON, hashes from git, Italian sentences). The real sessions have more of the first (English instructions and listings, minified JSON and camelCase names from the CAIP MCP tools).

Conclusion

For current models, p50k_base underestimates Claude's count. On 385 texts typical of a Claude Code session, p50k gives 1,793 tokens per text on average and Claude Opus/Sonnet/Haiku 5.5, Fable 5.2 and Opus 4.7 give 2,305. That is Σp50k/ΣClaude = 0.778: p50k is about 22% low, and 98% of texts are under. To approximate the real count, multiply the p50k figure by ~1.29. Prose needs more (×1.52, user prompts ×1.76); tool results and JSON need less (×1.23–1.26). The quoted claim was true for the previous tokenizer (Sonnet 4.5: 1.012, ±6.6% per text) and stopped being true with the tokenizer of Opus 4.7 and the 5.x family.

On two real sessions the gap is larger: 384 tokens per piece with p50k against 531 with Claude, Σp50k/ΣClaude = 0.723, so p50k is 28% low (×1.38 to correct) in both sessions and in every kind of content. The larger gap comes from the mix of content, not from a different behaviour on the same content. The sessions are dominated by English text written for the model (instructions, system prompt, tool schemas, agent and skill listings) and by minified JSON and camelCase names from MCP tools. The new tokenizer splits all of these much more finely than p50k. The corpus has more indented code, pretty JSON, hashes and Italian, where the two tokenizers are closer. The right factor therefore depends on what a session contains: ~×1.2 for logs and indented files, ~×1.4 for prose and tool definitions, up to ×1.9 for camelCase identifiers.

For the c4 analyzers, every "estimated" bucket in report.mjs (assistant output, tool_use inputs, tool results, instructions) comes out ~20–35% low on these models (~28% on the two real sessions). The residual of OTHER = ctx − Σ estimated grows by the same amount, so part of what it shows as "other / thinking" is really tokenizer error. Options: apply a per-category factor (the table above) and label the figures as calibrated for the 5.x tokenizer, or ask count_tokens when a token is available.

Not tested

  • Text inside real request structure: tool_result / tool_use blocks, system prompt and tool definitions add framing that this test removes on purpose. Here only plain text in one user message is counted, with the framing subtracted as count("x") − 1, which assumes "x" is one token (±1 token per text, which only matters for the shortest sentences).
  • Real sessions beyond the two measured with sessions.ts. Their texts are not stored; explain.ts re-reads them in memory from the original paths, so it can only be rerun where those files exist. The frozen corpus comes from this repo, where tool results are partly fixtures and partly generated from repo files.
  • Images in tool results (estimated by report.mjs from pixel area, not tokenized) and thinking (not stored in transcripts).
  • Languages other than English and Italian, non-Latin scripts, emoji, base64, minified JS, images and PDFs.
  • Counts of output tokens: the API counts input, and output may tokenize the same way, but that is not checked here.
  • Other offline encodings (cl100k_base, o200k_base) as alternatives to p50k.
  • Variance over time: count_tokens was called once per text and model, on 2026-11-19.
