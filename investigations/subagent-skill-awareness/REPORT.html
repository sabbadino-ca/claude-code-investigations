Is a subagent aware of the skills (name and description) the way the main conversation is, or must it name them in its frontmatter?

Key finding: a subagent gets the skill names and descriptions only if it has the Skill tool. With no tools: field it inherits the tool and gets the same skill_listing as the main conversation, with no skills: needed. With a tools: list, Skill must be in it; with tools: Read alone the subagent's context held no skill content. The skills: field does not change this: it injects bodies only and gives no listing. Same result in claude -p and the Agent SDK, Claude Code 2.1.310.

Question

No doc sentence prompted this; it is a question from the user. The sub-agents docs page, code.claude.com/docs/en/sub-agents, says the following (quoted from a WebFetch of the page, which summarises with a small model, so wording may be trimmed):

"This field controls which skills are preloaded, not which skills the subagent can access: without it, the subagent can still discover and invoke project, user, and plugin skills through the Skill tool during execution. To prevent a subagent from invoking skills entirely, omit Skill from the tools list or add it to disallowedTools."

"Each subagent starts with a fresh, isolated context window. It doesn't see your conversation history, the skills you've already invoked, or the files Claude has already read."

Testable form: does a subagent's own context contain the project skills' names and descriptions, as the main conversation's does, when its frontmatter has no skills: field? Does that depend on its tools: field? What does skills: add? Run modes: Agent SDK and headless claude -p. Interactive was not tested.

Each fixture skill carries DESC_MARK=<n> in its description and BODY_MARK=<n> in its body. A mark found in a context or an answer shows the text reached that model. The context is read from the transcripts: everything before the first assistant entry.

  • skill-alpha, skill-beta, skill-gamma: ordinary skills with unique marks.

  • probe-skilltool: tools: Read, Skill, no skills:.
  • probe-restricted: tools: Read, no skills:.
  • probe-preload: tools: Read, skills: [skill-alpha].
  • probe-inherit-hidden, probe-skilltool-hidden, probe-restricted-hidden: the same three tool variants (none, Read, Skill, Read), each with skills: [skill-hidden].
  • prompts/main.md: the strict main script. Either call the Agent tool once and return its answer verbatim, or (baseline) answer directly.
  • Two questions, in both drivers: list asks the agent to list every skill it knows (name | description, verbatim), its tools, and any BODY_MARK it can see, using no tool. invoke asks it to call the Skill tool for skill-beta and report the BODY_MARK, or say SKILL_TOOL_UNAVAILABLE.

Bundled skills, plugin skills and the account's skills also appear in the listing; only the fixture marks are judged.

  • skill-hidden (disable-model-invocation: true) was in no listing, main or subagent.
  • Invoke. probe-inherit and probe-skilltool called Skill for skill-beta and returned its BODY_MARK. probe-restricted reported SKILL_TOOL_UNAVAILABLE with TOOLS=Read and made no call.
  • The Skill tool result reads only "Launching skill: skill-beta". The body arrives in a separate message, so the judge reads body marks from the transcript, not from the tool result.
  • With skills: [skill-alpha] and no Skill tool, the subagent held alpha's full body but no skill list.
  • The listing in the subagent came with the Skill tool: given by default when tools: is omitted, or when Skill is named in tools:.
  • The user's own interactive observation matches: a subagent with no skills and no tools in its frontmatter knows the skill names and descriptions and can load them; once tools is given, Skill must be in it for the names and descriptions to be available.
  • Costs were small, roughly $0.03 to $0.12 per scenario.

  • Naming skill-hidden in skills: had no visible effect: its body was not injected in any of the three agents, and the rest of the picture is the same as without the field. The listing still followed the Skill tool.
  • The agents ran without an error. The docs say a skill with disable-model-invocation: true cannot be preloaded and that a missing or disabled skill is skipped with a warning in the debug log. The debug log was not read in these runs.

Conclusion

In Claude Code 2.1.310, in both claude -p and the Agent SDK, a subagent whose frontmatter has no tools: field receives the same skill listing (names and descriptions of model-invocable skills) as the main conversation, and can load a skill with the Skill tool, without naming any skill in skills:. When tools: is set, the listing is present only if Skill is in it; in the run with tools: Read alone, the subagent's context held no skill content. The skills: field does something else: it injects the full body of the named skills at startup and gave no name-and-description entry for them. The docs cover the Skill-tool discovery and the effect of omitting Skill from tools; they do not say the listing itself is what is withheld, which the transcripts show.
