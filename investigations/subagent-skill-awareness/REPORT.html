Controlling which skills the main conversation and subagents load

Goal. Decide which skills the main conversation sees and which a subagent sees, without editing the skill (you may not own it). That includes hiding chosen skills from main only, and hiding chosen skills from one specific subagent only, selectively rather than all or nothing. The control has to sit at the hosting level: a settings file, command-line arguments or SDK arguments. Skill and agent frontmatter can do part of it, but it needs edits to those files.

Rule that explains most results: a subagent gets the skill names and descriptions only if it has the Skill tool. A subagent with no tools: field in its frontmatter inherits every tool, the Skill tool included, so by default subagents see the same skill listing as the main conversation. With a tools: list, Skill must be in it; with tools: Read alone the subagent's context held no skill content. The skills: field does not change this: it injects bodies only and gives no listing.

Outcome for the two halves of the goal (Claude Code 2.1.310): a way was found to hide chosen skills from main only (the Agent SDK skills option, below). No option was found to hide chosen skills from a specific subagent, selectively. A subagent can only drop the whole listing (leave Skill out of its tools:) or preload bodies with skills:, which removes nothing from the listing. Hiding a skill from main and from all subagents together, selectively, is possible (skillOverrides, or disable-model-invocation: true in the skill).

Host-level controls, to hide a skill from main while a subagent keeps it:

  • Settings file (skillOverrides): does not meet the goal. off and user-invocable-only hid the skill from main and from the subagents alike, and skills: preload did not bring it back.
  • claude -p: only in a stateful mode. Plain claude -p "prompt" has no way to set a skill filter and there is no command-line flag. The filter works in headless streaming-input mode (--input-format stream-json), where the process stays up and reads stdin, so it is no longer one-shot, and an initialize control request carries skills. That protocol is undocumented as far as I found; the message was copied from the SDK source.
  • Agent SDK skills option: works. Main lists only the named skills; subagents are unaffected and can still preload a filtered-out skill through their own skills:.

Question

This began as a question from the user: is a subagent aware of the skills (name and description) the way the main conversation is, or must it name them in its frontmatter? It widened into the goal above. The sub-agents docs page, code.claude.com/docs/en/sub-agents, says the following (quoted from a WebFetch of the page, which summarises with a small model, so wording may be trimmed):

"This field controls which skills are preloaded, not which skills the subagent can access: without it, the subagent can still discover and invoke project, user, and plugin skills through the Skill tool during execution. To prevent a subagent from invoking skills entirely, omit Skill from the tools list or add it to disallowedTools."

"Each subagent starts with a fresh, isolated context window. It doesn't see your conversation history, the skills you've already invoked, or the files Claude has already read."

Testable form: what does each subagent configuration have in its context (skill names and descriptions, skill bodies), and which skill-level or host-level control changes what main and subagents see? In particular: can chosen skills be kept out of main only, and can chosen skills be kept out of one specific subagent's listing, without all-or-nothing and without editing the skill? Run modes: Agent SDK and headless claude -p (one-shot and streaming-input). Interactive was not tested. Results are reported as outcomes, with no confirmed or refuted label.

2. Skill-level controls (frontmatter)

These work, but each needs an edit to a skill file or an agent file, which is not what we want when we do not own the skill.

  • Agent tools: and skills: (table above): omitting tools: or including Skill gives the subagent the listing; skills: preloads a body.
  • disable-model-invocation: true on the skill hides it from main and from every subagent; naming it in skills: does not preload it.
  • user-invocable: false on the skill hides it from the slash menu only; main and subagents still see it, and skills: preloads it.

    claude -p

    • One-shot claude -p "prompt": no way to set a skill filter. No command-line flag was found in --help or the SDK source, and the only skill-filtering setting found is skillOverrides (above), which can be passed with --settings.
    • Streaming-input claude -p --input-format stream-json: the filter works, with an initialize control request carrying skills, sent on stdin before the user message. The process is long-lived: it keeps reading stdin until stdin closes, so this is no longer a one-shot run (the driver closes stdin once the result arrives). The input format, control_request and initialize are not documented on the headless page (read via WebFetch, whose summary may miss a section), and the message was taken from the SDK 0.3.310 source, so this route may change or be unsupported for direct use.

    Conclusion

    Hiding chosen skills from main only: found, through the Agent SDK skills option. Hiding chosen skills from a specific subagent, selectively: no option found among those tested. For a subagent the controls are all or nothing (tools: without Skill removes the whole listing) or add-only (skills: preloads bodies and removes nothing). Selective exclusion exists only for main and subagents together, through skillOverrides or disable-model-invocation: true. The SDK skills option does not reach subagents.

    By default (no tools: field) a subagent has the Skill tool and receives the same skill listing as the main conversation, in both claude -p and the Agent SDK; skills: adds a skill's body and no listing entry. Among the host-level controls tried, only the Agent SDK skills option hid skills from main while leaving them to subagents, with the skill files unmodified; the same filter reached claude -p only through the undocumented, stateful streaming-input protocol. The skillOverrides setting hid the skill from subagents too, and frontmatter controls need edits to files that may not be ours. The docs cover the Skill-tool discovery and the effect of omitting Skill from tools; they do not say the listing itself is what is withheld, which the transcripts show.

    Preload without the Skill tool (2026-10-26, headless): as expected. With the Skill tool removed (by tools: allowlist or by disallowedTools: Skill) and skills named in skills:, the named skill's body is in the context from the start, the other skills cannot be loaded, and no listing is injected. The two ways of removing the tool gave the same outcome.

    Not tested

    • Interactive terminal mode.
    • skillOverrides with name-only: not tested, since it only collapses a description and clearly does not help the goal. Also not tested: skillOverrides in the settings files themselves (only through --settings) and in the SDK.
    • Whether the Skill tool or /name still loads the skill under skillOverrides, and what the difference between off and user-invocable-only is for the user.
    • Whether the streaming-input initialize protocol is supported for use outside the SDK, and how stable it is across versions.
    • Several turns in one streaming-input process; each scenario sent one user message.
    • A way to hide chosen skills from one subagent: not found, and two more routes were not run. They are judged irrelevant to fine-grained listing hiding, by reasoning rather than by test: disallowedTools in an agent is about loading, not about listing (the docs mention it only for blocking the Skill tool as a whole; disallowedTools: Skill was tested on 2026-10-26, see above, and behaved like dropping Skill from tools:), and the SDK agents option's skills field is taken to be the same as the frontmatter skills:, a preload list (its type reads "skill names to preload").
    • Whether main's Skill tool rejects a skill filtered out by the SDK option (the SDK type comment says it does).
    • user-invocable: false together with disable-model-invocation: true.
    • skills: listing both a hidden and a normal skill (whether the normal one still loads), and the debug-log warning for a skipped skill.
    • User-level and plugin skills as seen by subagents; only project skills carried marks.
    • The SDK skills option as 'all', with a list of several names, or with plugin-qualified names.
    • Background subagents, nested subagents, and built-in agent types.
    • The 32-name cap on skills:, and the effect of many skills on the listing's size.
    • Other Claude Code versions; only 2.1.310 ran.
    • One run per scenario and driver, with Sonnet; answers depend on the model reporting what it sees, which is why the transcripts, not the answers, are the evidence for what the context held.
