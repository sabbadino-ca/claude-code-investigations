Does claude -p --output-format stream-json report the real output-token count?

Question

No doc sentence: a practical bug report. An integration launches claude -p --output-format stream-json --verbose without --include-partial-messages and reads message.usage.output_tokens from the assistant events. It sometimes gets 4 or 6 output tokens for a long answer. Hypothesis: those events carry the usage of the API message_start event, not the final count. The final count only arrives in the API message_delta event, and that event is forwarded (as stream_event) only with --include-partial-messages.

Confirmed if, for every API message (message.id), the assistant events carry a value far below the real one, while with the flag message_delta.usage.output_tokens, summed per message, equals result.usage.output_tokens. Run mode: claude -p only.

Follow-up questions, for a chat that spans several processes (claude -p, then claude -p --resume <id> twice):

  • A. Does each process's result (usage, modelUsage, total_cost_usd) cover that process only, or the conversation so far?
  • B. Once the chat is over, can every token (input, cache, output) be recovered from the session files alone, without having watched the stream?

Why: the assistant event is emitted before message_delta

From the partial-mode timeline (multi-tool-partial-r1.jsonl, ms from start):

  1792 message_start      id=…C1Rkp1di  output_tokens=20
  2034 ASSISTANT          …C1Rkp1di tool_use  output_tokens=20  stop_reason=null
  2244 ASSISTANT          …C1Rkp1di tool_use  output_tokens=20  stop_reason=null
  2438 ASSISTANT          …C1Rkp1di tool_use  output_tokens=20  stop_reason=null
  2457 message_delta      output_tokens=246
  2459 message_stop
  …
  9767 RESULT             output_tokens=1374   (= 246 + 206 + 922)
  • Claude Code emits one assistant event per content block, when that block ends, so before the API sends message_delta.
    • Each event carries a copy of the usage from message_start. There, output_tokens is only the handful of tokens counted so far (1–20 here).
    • stop_reason is null in every assistant event of all 30 runs.
  • The same partial usage is repeated on every event of a message, and all of them share its message.id.
    • A message with thinking emits two assistant events (thinking, then text). A message with 3 parallel tool calls emits three.
    • Summing over events instead of over message.id therefore doubles or triples that wrong number. That is how a 4000-token essay shows up as 4 or 6: 2 + 2, or 3 + 3.
  • The flag changes nothing in the assistant events: they carry the same partial snapshot in both modes. It only adds the stream_events, among them message_delta. Its usage.output_tokens is the final per-message count.
  • The session transcript .jsonl holds the final count for every message, repeated on each content-block entry. So Claude Code knows the correct value; it just doesn't update the stream event it has already sent.
  • system:thinking_tokens events (estimated_tokens) arrive during thinking in both modes. They are an estimate of thinking only, not a usage count.

Conclusion

Confirmed. In Claude Code 2.1.327, the assistant.message.usage.output_tokens of claude -p stream-json is the message_start snapshot, never the final count, with or without --include-partial-messages.

Whether you call it a bug or a design limitation, the field is unreliable for output tokens: the event goes out before the API has reported them. The reliable sources:

  1. result.usage.output_tokens (or result.modelUsage): the exact total of the whole -p invocation. It needs no flag. This is the simplest fix when one total per run is enough.
  2. stream_event → message_delta.usage.output_tokens, with --include-partial-messages: exact per API message, in real time.
    • Attribute it to the message.id of the preceding message_start.
    • Take one value per message.
  3. The session transcript, after the fact: exact per message, but deduplicate by message.id.

Whatever the source, never sum usage over assistant events. Group by message.id.

Multi-process chats. Each process's result.usage covers that process only. modelUsage and total_cost_usd are session running totals: take the last one, don't sum them.

Subagents appear in neither result.usage nor the stream's stream_events. At runtime they appear only in the cumulative per-model modelUsage / total_cost_usd. Afterwards they appear exactly in subagents/agent-*.jsonl and in cost-state.

Edge cases.

  • With background subagents one process emits several result events: sum result.usage over all of them.
  • Nested subagents land in the same subagents/ folder.
  • --thinking-display summarized and --forward-subagent-text change nothing.
  • A max_tokens stop is counted exactly, including Claude Code's automatic continuations.
  • The one gap: an API message cut off by killing the process is recorded nowhere, not in the stream, the files or cost-state. Those tokens are lost to any accounting.

Real sessions. In a real 2.1.319 session (main + 2 subagents), the deduplicated file usage is exact and equals cost-state. A CAIP-report built from the same session estimates only 48% of the output tokens. Reading usage.output_tokens per message.id beats tokenizing the text.

Cost per agent. Neither the files nor the stream carry a cost per subagent. Pricing each agent file's deduplicated usage with the list prices reproduces Claude Code's own costUSD exactly, per model and in total, so it is the way to cost each subagent. When subagents share the main session's model, it is the only way.

After the chat is over, the session .jsonl holds everything, with no need to have watched the stream:

  • Per message: the assistant entries, deduplicated by message.id.
  • Per chat: the last cost-state entry (cumulative cost and per-model usage, thinking included).

Not tested

  • Agent SDK (includePartialMessages) and interactive mode.
  • Whether the API bills the tokens of a message cut off by a kill (the session records nothing of them). A kill that hits a subagent mid-message. Prices above 100K-token prompts (Haiku 5.5's higher tier), fast mode, and models other than Haiku 5.5 / Sonnet 5.5 in the cost check. Also --input-format stream-json.
  • --fork-session, --continue, and a --resume run after compaction.
  • Other models and effort levels.
  • Runs that hit max_tokens or are interrupted, where message_delta or result may be missing.
  • Input and cache fields in the first batch: only output_tokens was compared there. The resume run compares all four fields.
