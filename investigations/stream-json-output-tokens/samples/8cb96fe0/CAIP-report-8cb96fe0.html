One exception survives inside Tools, described below.
Work excl. subagents
The agent's own effort — its own thinking and its own tool calls. Nothing its children did, and no time spent waiting on them.
Work excl. subagents %
That own effort as a share of all agent work in the conversation. Own work counts each agent exactly once, so unlike the incl. column these shares are disjoint and add up to 100%.
Work incl. subagents
The same, plus every descendant's own work, summed over the spawn tree (parentAgentId) and not over how long the parent's Agent calls took: an agent spawned in the background does not block its parent, so the two are unrelated. Rows overlap by design — a parent's figure contains its children's rows, so this column must not be summed down the table.
Main session: thinking gaps are capped at 15 minutes
When a main session is left and resumed later, the first entry after the break is often an assistant reply, so the whole break would count as Model Thinking. For the main session only, any single thinking gap counts at most 15 minutes; the rest goes to idle, outside Work. Subagents are never capped: when one is resumed, the gap ends with a user message, which already counts as idle.
The one exception: permission approvals sit inside Tools, and therefore inside Work. Work is meant to exclude human time in every form, and it does so for every form the transcript makes visible: an AskUserQuestion round trip and the gaps between turns are both identified and dropped. Approvals are different. When a tool call waits for the user to allow it — the default permission mode — no separate entry is written: the wait happens inside the very same gap as the call's execution, so a slow tool and a tool awaiting consent are byte-identical in this data. There is no way to separate them after the fact.

Practically it is usually minor — tens of seconds across dozens of calls in a typical run — but it scales with how often the agent was interrupted for consent, so read Work as a slight over-estimate. Sessions run with broad pre-approval, or by agents whose tools are all auto-allowed, carry almost none of it; a session where every command was confirmed by hand carries a lot.

How context is measured

Final ctx
Taken from the last assistant message of each transcript: its whole prompt (input + cache_read + cache_creation, exact) plus that reply's own text, tokenized. It is the occupancy at the end of that agent's run, not its cumulative token spend.
The four percentages are not the same measure
Context: Share of total divides by all agents' context; Work excl. subagents % divides by all agents' work; in a context drill-down, % of its ctx divides by that one run's final context, and % of preamble (inside the expanded Preamble row) by that run's exact preamble — so each of those two tables sums to 100%. Only the table's ctx column is measured against the assumed window (set with --window) — that is the compaction-risk reading, and it is meaningless once runs are aggregated.
The context drill-down describes ONE run. Click a row's context cell to see where that agent's context came from. When a role ran several times the drill-down shows its fullest run — the one that ended holding the most context — and every table in it belongs to that same run: the seven buckets (which sum to its Final ctx), the Preamble row, which expands on click into the itemised preamble, the Loaded mid-run table (skills and instruction files that arrived after the first call, with the call they arrived after and how many later calls carried them), and the per-tool table. Sibling runs are not blended in; open the runs drill-down to see them individually.
Preamble is everything already in the window before the agent had said anything: its agent definition, the harness system prompt, the schemas of every tool it was given, CLAUDE.md and rules, the skill and agent listings — and the task prompt it was handed. It is measured as the prompt size of the agent's very first API call, so it is exact.

Its itemisation is an estimate, and how much of it is possible depends on what the transcript recorded. The agent definition, system prompt and tool schemas come from a prompt_snapshot entry, written by Claude Code from 2.1.260 in main sessions and from 2.1.267 in subagents. CLAUDE.md and rules come from a separate instructions entry, already present in some earlier subagent transcripts (e.g. 2.1.263) but not in all (none in 2.1.260). Whatever the recorded items do not explain is shown as Unattributed, signed rather than spread over the items: with a snapshot it is mostly request framing and tokenizer drift and can go slightly negative; without one it also holds the agent definition, system prompt and tool schemas, and the drill-down says so.
How exact each bucket is. Preamble is exact. Assistant replies, Tool results, User messages, Skills loaded mid-run and Instructions loaded mid-run are tokenized from the text actually written to the transcript with gpt-tokenizer's p50k_base (vendored — no install, no network): close, but OpenAI's BPE rather than Claude's, so read them as good estimates and not as billing figures. Token counts reported by the API per message are not usable — most messages carry only a placeholder.

Other is the remainder, so the buckets always sum to Final ctx without anything being estimated into existence. It is not a rounding error: across multi-call runs measured on this machine it was 13–63% of a run's context, dominated by thinking, whose text transcripts never store. It also holds the remaining attachments, system reminders and per-request overhead. It shows 0 for a run with a single API call, by construction, and is clamped at 0 when the tokenized buckets over-count; when they over-count by more than 1% of Final ctx the Final ctx row says so and gives the real sum. Images in tool results (screenshots read with Read) are counted by pixel area, width × height / 750, never by the length of their base64 encoding.
Instructions, skills & prompts — all runs adds up every preamble item and every mid-run load over all runs (the main session included), so a CLAUDE.md that nine agents loaded appears once, with 9 in Runs. Tokens is the item's size in the single run where it was largest. Held is the sum over runs — window space taken, in separate windows, never one. Re-sent is tokens × the API calls that carried the item: a preamble item rides on every call of its run, a mid-run load on every call after it. It is the input volume the item caused — the closest figure to “tokens spent” on it — mostly billed as cache reads, and it assumes nothing was dropped by a compaction. Task prompts and agent definitions are grouped by agent type, since their text differs per run.
