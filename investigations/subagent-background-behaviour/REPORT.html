Does a launching subagent wait for its nested background subagent?

Claim under test, from https://code.claude.com/docs/en/sub-agents#let-subagents-spawn-their-own-subagents:

In an interactive session ... a subagent that launches background subagents waits for their results before it finishes. In non-interactive mode and the Agent SDK, the launching subagent doesn't wait, so a nested background subagent that finishes after its launcher has ended reports to your main conversation instead.

Two follow-ups use the same harness: whether N foreground subagents run in parallel when main spawns them in one message, and whether resuming a completed subagent with SendMessage is sync or async for main.

Setup

main (SDK query or claude -p)  --Agent-->  launcher  --Agent-->  slow-worker

Fixture (this folder):

  • .claude/agents/launcher.md: its only tool is Agent. It spawns one slow-worker, then ends its turn right away with LAUNCHER_FINAL: <token or NO_WORKER_RESULT_YET>. With no other tools it cannot wait on its own, so any waiting you see comes from the harness, not from the model.
  • .claude/agents/slow-worker.md: its only tool is Bash. It runs a 40 s Node timer that prints a random WORKER_TOKEN=<n>. Only the worker knows the token, so if the token shows up somewhere, the worker's result got there.
  • .claude/agents/resumable.md: draws a hidden NONCE on its first run and ends with FIRST_RUN_DONE; when resumed with CONTINUE it waits 20 s and returns RESUMED_FINAL NONCE=<n>.
  • prompts/: the main prompts, rendered by the drivers. nested-main.md (experiment.ts, nested-cli.ts), parallel-main.md (parallel.ts, parallel-cli.ts), resume-main.md (resume.ts). prompts/parallel-fanout.md is the reusable fan-out instruction distilled from the parallel results; no driver reads it.

Drivers (this folder; the shared harness is lib/claude-home.mjs):

  • experiment.ts runs main through the TypeScript Agent SDK:
    • A PreToolUse hook on Agent sets run_in_background for each scenario. It also records whether the model had already chosen that value; in every run it had.
    • SubagentStart, SubagentStop, and PostToolUse hooks, plus the task_started, task_notification, task_updated, and background_tasks_changed stream events, give the timestamps.
    • The prompt is streaming input that stays open until all background work has finished (open), is closed after the first result (close), or is a plain string (string, the 1shot-* scenarios).
  • nested-cli.ts: the same one-shot matrix through the installed claude -p, with command hooks logging to <run>.hooks.jsonl. Sync/async comes from the prompt alone; no hook changes any input.
  • parallel.ts / parallel-cli.ts: main is asked to emit N slow-worker Agent calls in one message. Foreground is forced by CLAUDE_CODE_DISABLE_BACKGROUND_TASKS=1 and CLAUDE_CODE_FORK_SUBAGENT=0.
  • resume.ts: main spawns resumable with run_in_background: false, then resumes the same instance with SendMessage to its agentId. forced sets the two variables above; default sets none.

Scenarios are named outer-inner. outer is how main spawns the launcher and inner is how the launcher spawns the worker; fg means foreground and bg means background. direct-* has main spawn the worker itself.

Result

The claim is true for the Agent SDK and for claude -p.

  • Inner background (fg-bg, bg-bg): the launcher ended at about 5–6 s with NO_WORKER_RESULT_YET. Its SubagentStop reported 1 background task still in flight, and the harness never woke it again (one stop only). The worker finished at about 52 s. Its task_notification was delivered to the main conversation as an injected turn (result.origin.kind = "task-notification"), and main reported the token.
  • Inner foreground (fg-fg, bg-fg): the launcher's Agent call blocked until the worker finished, and the launcher's final message contains the token. This is the expected foreground behavior and acts as the control.
  • How main spawns the launcher (fg or bg) made no difference to whether the launcher waited.

Main conversation

results/<run>/<scenario>.main-transcript.txt holds what the main model was actually fed, taken from the session transcript.

  • Launcher in the foreground: main's Agent call blocks until the launcher ends, then main ends its turn. Main waits for the launcher only, never for the background worker.
  • Launcher in the background: main's Agent call returns Async agent launched immediately. Main ends its turn while the launcher is still running.
  • Notification turns: every background subagent that finishes later, including the nested worker, is injected into main as a new user turn. The turn holds a <task-notification> block with <result>...</result> and has origin.kind = "task-notification", and it produces its own result message.
  • main-busy: the worker finished while main was still inside its own 70 s command. The notification was queued (a queued_command attachment) and folded into main's current turn after the command returned. There was no separate turn: one result answered both the prompt and the notification. (In the rerun main's answer carried only the MAIN_GOT_NOTIFICATION line, not also MAIN_TURN_DONE; the delivery was the same.)
  • main-close / main-string: closing the input after the first result, or using a plain string prompt, did not kill the worker. The CLI stayed alive until the worker finished, ran the notification turn, emitted a second result, and only then ended the query() iterator, at about 54 s.

Does the WORKER_TOKEN reach main before the session ends? (1shot-* scenarios)

These scenarios use a plain string prompt, so nothing in the script holds the session open. Every chain was tested: direct, and through the launcher, with each sync/async combination. In all of them the CLI stayed alive until the worker finished, main received the token, and only then did the session end, about 0.3 s after main's last answer.

  • Sync all the way (main →fg worker, main →fg launcher →fg worker): the token comes back in the prompt's own turn, as the return value of the Agent call. There is a single result.
  • Any async link in the chain: main's prompt turn ends with NONE. The token arrives later in a task-notification turn, with a separate result per notification:
    • When the launcher is async and the worker is sync, the token comes inside the launcher's notification.
    • When the worker is async, the token comes in the worker's own notification, delivered straight to main and bypassing the launcher, which has already ended.

Headless claude -p vs the SDK (nested-cli.ts, parallel-cli.ts)

Behaviour is identical:

  • With an async worker, the launcher doesn't wait.
  • The worker's callback goes to main, never to the launcher.
  • The process stays alive until every callback has been handled.
  • Each chain delivered the token the same way (sync or callback).

One stream difference: in -p mode every result line is held back until all background work has finished, then all of them are written together just before exit. Main's answer text still streams live when it is written. The SDK emits each result as soon as its turn ends.

Parallel foreground fan-out (parallel.ts, parallel-cli.ts)

With 5 workers, in both runs of both drivers: main emitted all 5 Agent calls in one message, all ran in the foreground, the workers started within about 1.5 s of each other and finished in about 48–50 s of wall time (against about 240 s of summed worker time), and main had all 5 tokens before it answered.

Resuming a completed sync subagent: sync or async for main? (resume.ts)

env what SendMessage returns how main gets the resumed run's reply verdict
forced (CLAUDE_CODE_DISABLE_BACKGROUND_TASKS=1, CLAUDE_CODE_FORK_SUBAGENT=0) blocks ~22–23 s, then Resumed agent. Its final report follows… + the report inline, as the tool result; a single result SYNC
default (no env vars) returns in under 0.25 s with Resuming agent <id>, resumedAgentId main ends its turn ("waiting…"); the report arrives later as a <task-notification> turn and gets a second result ASYNC

The same pattern held for the SDK and for claude -p. In every run the resumed subagent was the same instance: one transcript, and the nonce matched. A SendMessage resume ignores how the subagent was first spawned. It runs in the background, as the docs say, unless background tasks are disabled. The task_started event for the resume reports is_backgrounded: true in both modes. SendMessage is a deferred tool, so main first loads it with ToolSearch.

Conclusion

In the Agent SDK and in claude -p, a subagent that launches a background subagent does not wait for it: the launcher ends, and the nested subagent's result is delivered to the main conversation as a task-notification turn. The session stays alive until that delivery has happened, even with a one-shot prompt. Foreground subagents spawned in one message run in parallel, and a SendMessage resume is async unless background tasks are disabled. Confirmed on Claude Code 2.1.296 (SDK and -p) and 2.1.299 (-p).
